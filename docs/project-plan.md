# ジャングルパング再現プロジェクトプラン

策定日：2026年10月1日  
状態：企画・計画段階。ゲーム実装、原作の実機操作、動作・音声の計測は未実施。  
対象：昔のLINEトークルーム内で遊べた「JUNGLE PANG」を参考にした独立動作版。

## 1. 目的と完成イメージ

塔の最下段を見て、対応する左右のボタンを素早く押し、短時間で得点を競う体験を再現する。完成の中心は機能数ではなく、入力の反応、先読みのしやすさ、塔が詰まるテンポ、ミスの重さ、連続正解の気持ちよさとする。

暫定的に、スマートフォンの縦画面ブラウザを主対象、PCブラウザを補助対象とする。最初はLINEログインや旧サービスへの接続に依存せず、単体で一通り遊べるものを作る。対象端末・公開方針は最初の工程で確定する。

第1版では「起動 → 短い説明 → 40秒のプレイ → 結果 → 再挑戦」が完結し、端末内に自己ベストが残る。独自の育成、課金、ガチャ、ステージ制、新ルールは追加しない。

## 2. 原作について確認できたこと

| 項目 | 確認内容 | 根拠 |
|---|---|---|
| LINE内での提供 | 2017年9月21日の公式告知に、トークルームの＋メニューから起動できるだるま落としゲームとして掲載 | S01 |
| 操作 | 中央の塔の最下段と同じキャラクターを、画面下の左右のボタンから選ぶ | S03 |
| 制限時間 | 紹介記事および掲載されたルール画面では40秒 | S03、S04、S05 |
| ミス | 一時的にプレイできなくなる一方、時間は進むと紹介されている | S03 |
| 画面構成 | 縦方向の塔、左右の大きなボタン、残り時間、得点、コンボ表示を確認 | S02 |

公式の宣伝画像と実プレイの紹介画像には、キャラクターの組合せや画面構成に差がある。最初の工程で再現対象となる版と基準資料を決め、別版の仕様を無条件で混ぜない。

### まだ確定していない仕様

正解1回の点数、コンボの成立・加点・解除条件、ミス硬直の長さ、正解後の入力制限、出現確率と連続出現の偏り、塔の移動時間、同時押し・押しっぱなしの扱い、ポーズ時の挙動、キャラクターの切替条件、音声演出の詳細は未確定。

これらは「原作で確認済み」「資料からの推定」「再現版の暫定値」に分けて管理する。資料が得られない数値を原作の仕様として断定しない。資料で確認できないまま残った項目は、近似仕様として完成報告に明示する。

## 3. 再現範囲

### 第1版に含める

縦画面レイアウト、2種類の駒と左右入力、塔の表示と補充、40秒タイマー、正誤判定、ミス硬直、得点とコンボ、正解・ミス・終了演出、説明画面、結果画面、再挑戦、自己ベスト、音量設定、スマートフォン実機検証を対象とする。

得点式と硬直時間は調査後に調整できる構造にする。未確定の間は、仮の採点方式を使った検証ビルドとして扱い、原作再現完了とはしない。

### 第1版完成後に検討する

スコアカードとURLによる共有、友人内ランキング、ホーム画面追加・オフライン起動への対応、アプリとしての配布、LINEとの連携を必要に応じて検討する。独立アプリ版などに固有の機能は、対象版に存在することを確認するまで採用しない。

### 初期対象外

旧ランキング・旧アカウントの復旧、旧サーバーへの接続、課金、広告、ガチャ、育成、リアルタイム対戦、大量のキャラクター、独自ステージ、原作にない救済アイテム。

## 5. ゲーム仕様と重要な設計方針

### 基本ループ

最下段の種類を確認し、対応するボタンを押す。正解ならその1個を除去し、塔を1段詰め、次の対象を表示する。ミスでは短い操作不能と視覚・音声のフィードバックを与える。制限時間終了時に入力と得点を確定し、結果画面へ移る。

ミス時に最下段を残すこと、ロック中の入力を破棄することは暫定方針とし、原作の挙動が確認できた場合に照合する。原作で確認されていないライフ減少、追加の時間減算、強制終了を勝手に足さない。

### 入力の反応

タップを受けてから画面が反応するまでの遅れを最優先で調整する。正解演出が終わるまで次の入力を待たせるような、原作で確認されていない制限を入れない。

両手での高速交互入力を想定する。タップとマウス互換イベントなどの二重計上を防ぎつつ、本来別々の連打をまとめて捨てない。押しっぱなし、左右同時入力、複数指、ボタン外からのスライド入力について扱いを決め、入力ログで確認する。

PCではキーボードの左右キー等を補助入力に使う。PC入力を搭載する場合、端末間の比較やオンラインランキングの条件は別途決める。

### 塔と視認性

最下段だけでなく、次の数段を先読みできる状態を保つ。表示段数と相対サイズは基準資料を計測して決める。長い画面だからといって先読みできる段数を無制限に増やさない。

駒の状態は論理的な順番として管理し、落下は演出として描画する。物理演算によるランダムな揺れ、積み崩れ、待ち時間は追加しない。見た目の最下段と内部判定の対象がずれないようにする。

### 時間と状態管理

制限時間をフレーム数に依存させない。準備、プレイ中、ミス硬直、終了、結果の状態を明確に分ける。時間切れ後の加点、終了演出中の入力受付、再挑戦でのタイマー二重起動を防ぐ。

アプリ切替や画面離脱後の扱いはM0で定義する。初期案ではプレイ中断として終了させ、復帰による時間延長を認めない。原作のポーズ挙動が確認できた場合は、再現方針と記録の有効条件を調整する。

### 得点とコンボ

採点処理を演出や入力処理から分離する。基礎点、コンボ加点、コンボの解除条件、演出が出る節目を設定データにまとめる。試作中の仮の点数を原作と同じものとして表示・説明しない。

## 6. 見た目と音の制作計画

### 画面の優先順位

中央の塔、画面下の左右ボタン、上部の残り時間と得点を主役にする。背景の密度、明度差、ボタンの大きさ、塔の位置を基準資料と比較する。スマートフォンのブラウザUIや画面下端でボタンが隠れないよう検証する。

### 最小の制作物

最初は2種類の駒、対応する左右ボタン、背景1セット、時間・得点表示、正解・ミス・コンボ・終了の演出、タイトル・結果画面に必要な要素を制作する。原作で複数の組合せや背景変更が確認された場合に、必要な差分を追加する。

仮素材段階でも、色だけでなくシルエットなどで2種類を識別できるようにする。最初から高精細な素材を大量制作せず、入力とテンポの合格後に本制作へ進む。

### 音

正解、ミス、節目、残り時間警告、終了などの音とBGMの必要性を資料から整理する。原作に存在するか未確認の音を原作の仕様と断定しない。

正解音は高速連打でも耳障りな重なりや音割れが起きないよう調整し、ミス音は明確に聞き分けられるようにする。操作音がBGMに埋もれないこと、初回操作後に音が出ること、アプリ切替後の復帰、ミュート設定の保存を実機で検証する。音源が未確認なら仮音であることを明示する。

## 7. 推奨する技術構成

TypeScript＋Phaser＋Viteを第一候補とする。Phaserはモバイル／PCブラウザ向けの2DゲームとTypeScript利用を公式に案内している。Viteは開発用サーバーと配布用のビルドを提供する。[S07、S08]

初期版は静的配信と端末内保存で成立させ、専用APIサーバー、オンラインDB、ログイン、LINE SDKは使わない。ライブラリと実行環境は着手時点で互換性を確認し、バージョンとロックファイルを固定する。

プログラムは次の責務を分ける。

| 領域 | 責務 |
|---|---|
| ゲーム本体 | 列の順番、正誤判定、時間、得点、コンボ、状態遷移 |
| 入力 | タッチ・マウス・キーボードの正規化、重複防止、イベント順序 |
| 表示・音 | 駒、背景、ボタン、アニメーション、効果音、BGM |
| 保存 | 自己ベスト、音量、設定の保存と読み出し |
| 検証 | 固定した出現列、入力ログ、再生、結果比較 |

単体テストはVitest、画面遷移や画面サイズ別の自動テストはPlaywrightを候補とする。Playwrightのモバイルエミュレーションは画面サイズやタッチ設定などを模擬するためのものであり、本計画では実機タッチ・音声・描画の検証を別工程にする。[S09、S10]

## 8. 開発工程と合格条件

以下の工数は、1人がAI補助を使い、小規模な2D版を制作する場合の計画上の概算。納期保証ではなく、資料入手、素材制作、対象端末数によって変動する。原作素材の許諾取得や大規模な描き直し、アプリストア対応、オンライン機能は含まない。

| 工程 | 主な作業 | 工数目安 | 合格条件 |
|---|---|---:|---|
| M0：再現基準の確定 | 基準版・画像・動画を選定。仕様と未確認項目を整理。対象端末と素材方針を確定 | 4〜8時間 | 何を再現し、何が未確定かが仕様表で分かる |
| M1：判定と時間の試作 | 仮素材で列、左右判定、タイマー、得点、ミスを実装。固定入力によるテストを追加 | 6〜10時間 | 40秒で終了し、同じ条件から同じ結果を得られる |
| M2：スマートフォンでの操作調整 | 両手入力、連打、塔の詰まり方、硬直、判定と描画の同期を調整 | 8〜14時間 | 基準端末で入力落ち・二重計上・見た目と判定のずれがなく、テンポ評価に合格 |
| M3：画面・演出・音 | 必要最小限の完成素材を用意。タイトル、ゲーム、結果の見た目と音を整える | 10〜18時間 | 連打中も読める、反応が重くならない、音が破綻しない |
| M4：1本のゲームとして仕上げる | 説明、再挑戦、自己ベスト、音量保存、読み込み・失敗時の扱いを実装 | 4〜8時間 | 起動から再挑戦まで仮操作なしで完結する |
| M5：受入試験・修正 | 端末差、時間切れ、画面離脱、再起動、連続プレイ、音出し、素材確認 | 8〜14時間 | 重大不具合がなく、未確定仕様と検証範囲を明示して第1版を確定 |

基本作業の合計は40〜72時間。約20〜25％の手戻り余裕を含め、50〜90作業時間程度を初期予算とする。M0終了時とM2終了時に再見積もりする。

依存関係はM0→M1→M2→M3→M4→M5を基本とする。M2で操作感が合格するまでは、本格的な素材量産やオンライン機能に進まない。素材の資料整理と仮の音探しは並行してよいが、ゲーム仕様を別々の担当が独断で変更しない。

M0の調査はまず4〜8時間で区切る。取得できない資料の探索だけで全体を止めず、未確定値を外部設定化してM1へ進む。一方で、原作との一致が確認できていない項目は、完成時にも確認済みに格上げしない。

## 9. 検証計画

### 自動テスト

固定した出現列と時刻付き入力を使って、同じ結果が再現できるようにする。最低限、全正解、最初にミス、途中でミス、硬直中の入力、時間切れ直前・直後、連続リトライ、保存済みデータの読み込み失敗を試験する。

30／60／120fpsを想定した描画条件でも、同じ論理時刻の入力列に対する得点・列の進行・終了判定が一致することを確認する。入力の自動試験と、人が実機で押したときの感触は別の検証として扱う。

### 実機テスト

| 観点 | 第1版の受入基準案 |
|---|---|
| 通常操作 | 正しい入力で必ず1個だけ進み、無関係な操作では得点しない |
| 高速入力 | 合成入力15回／秒の試験で欠落・二重計上がない。別途、実機で両手連打を確認する |
| 応答 | 基準の60Hz端末で、入力受付から最初の視覚反応まで原則2フレーム以内を目標に測る。タッチ機器全体の遅延とは区別する |
| タイマー | ミス硬直中も時間が進み、終了後に加点しない |
| 判定と表示 | 塔の移動中も、見えている対象と判定対象が矛盾しない |
| 画面 | 小画面・縦長画面・ブラウザUI変化で重要情報とボタンが隠れない |
| 継続利用 | 20回以上の連続リトライで、音・タイマー・イベントが重複せず、継続的なメモリ増加がない |
| 復帰・保存 | アプリ切替、再読込、音声復帰、設定・自己ベストの保存が定義どおり |
| 体験 | 基準資料との比較と原作経験者の試遊で、先読み・操作・ミス・再挑戦のテンポを評価する |

15回／秒、2フレーム、20回リトライは本プロジェクトの試験目標であり、原作の実測値ではない。対象端末を確定したうえで測定条件を記録する。

記録する証拠は、ビルド識別子、端末・OS・ブラウザ、試験条件、プレイ動画、入力と判定のログ、合否、未修正項目とする。平均fpsや画面キャプチャだけで操作感の合格を代替しない。

## 10. 主なリスクと対策

| リスク | 対策 |
|---|---|
| 資料の版違い・仕様不足 | 再現対象の版を固定。資料の種類・日時・確度を記録。数値は設定で差し替え可能にする |
| ルールは合うが感触が違う | 見た目より先に実機入力と塔のテンポを検証。原作経験者の試遊をM2に置く |
| 演出による入力遅れ | 判定と演出を分離。連打試験と入力ログを継続的に実施する |
| 端末で見え方・音・操作が変わる | 基準端末を決め、対応を公称する環境は実機で検証する |
| 素材の利用条件が不明 | 初期は仮素材。公開前に素材台帳と利用根拠を確認する |
| 機能追加で終わらない | 第1版を40秒の単体ゲームに固定。追加機能は別の工程にする |

## 11. 素材と公開の扱い

ゲームのルールやアイデアの再現と、原作の画像・音楽・プログラム等の流用は分けて考える。著作権ではアイデアそのものと創作的な表現は区別され、著作物の利用は許諾が原則で、例外には条件がある。[S11、S12]

したがって、原作キャラクター、ロゴ、背景、BGM、効果音を自由に再配布できる前提にはしない。個人用か公開版か、どの素材をどの条件で使うかを決める。公開する場合は利用許諾のある素材または独自の表現を用い、原作・LINEの公式復活版と誤認させる表示を避ける。非営利やサービス終了を利用許諾の代わりに扱わない。

必要に応じて権利者や専門家に確認する。素材の利用方針が未決定でも、仮素材による操作と時間の試作は先に進める。

## 12. 成果物と進捗管理

### 本計画の後に制作する成果物

ゲームのソースと起動手順、配布用ビルド、出典付きの原作仕様表、未確定仕様一覧、設定データ、使用素材と利用条件の台帳、単体・自動操作テスト、実機確認記録、既知の差分・不具合一覧を残す。

進捗は「実装した」だけでなく、「どのビルドをどの端末で何を確認し、何が未確認か」で報告する。自動試験の合格、実機での操作確認、原作への忠実度を分けて評価する。

第1版の完了条件は、主要機能がつながっていること、重要試験が合格していること、基準端末で操作感を確認していること、原作との差分が明示されていること、公開する場合の素材確認が済んでいることである。

### 最初の着手内容

M0で基準資料・未確定項目・対象端末を決める。その直後に、仮の2種類の駒、左右ボタン、40秒タイマー、正誤判定、短いミス硬直、結果・再挑戦だけを持つ試作を作る。スマートフォンで直接操作し、塔の先読みと連打の感触を確認してから、完成素材と周辺機能に進む。
